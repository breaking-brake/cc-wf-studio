# 製品価値の定義

> **状態: AI が作成した叩き台。人間が改訂する前提。**
> 以下は README・`IMPLEMENTATION_PLAN.md`・実装(ノード定義、CLI サブコマンド、
> MCP ツール)から読み取れる事実をもとに、価値の構造を再構成したものです。
> 事実の記述と、私の解釈による構造化が混在しています。**柱の切り方こそが
> この文書の本体**なので、納得いかない箇所は遠慮なく組み替えてください。
>
> **英語版**が `docs/product-value.md` にあります。エージェントが読むのは
> 英語版なので、どちらかを変えたら両方を揃えてください。この日本語版は
> リポジトリオーナー(日本語話者)が内容を判断・保守するためのものです。

## この文書の位置づけ

品質担保をトップダウンで設計するための最上位文書です。3階層の1段目にあたります。

```
【1段目】製品価値      ← この文書。何のためにあるか、何を約束しているか
    ↓
【2段目】実現機能      どの機能がその価値を実現しているか
    ↓
【3段目】担保          その機能が壊れていないことを、何が保証しているか
```

2段目・3段目は別文書に分けます。**1段目が曖昧なまま下を作ると、
「テストしやすいものをテストする」に流れる**ため、まずここを固めます。

## 1. 存在理由

### 解決している課題

AI コーディングエージェントに複雑な仕事をさせたいとき、その手順の設計は
プロンプトの試行錯誤になりがちです。**人間は図で考えるのに、エージェントは
Markdown を読む** —— この表現形式の断絶が、試行錯誤の正体です。

頭の中の「まずAして、結果次第でBかC、Bなら別のエージェントに投げる」という
構造を、いきなり散文のプロンプトに落とし込む作業には、次の困りごとが伴います。

- 全体像が見えないまま書くので、分岐や依存の抜けに気づけない
- 書いたものが意図どおり動くか、実行するまで分からない
- エージェントを乗り換えるたびに、書式に合わせて書き直しになる

### 提供している価値(一文)

> **キャンバス上で視覚的に設計したワークフローが、そのまま AI エージェントが
> 理解して実行できる成果物になる。**

README のタグライン「You think visually. AI thinks in `.md`.
CC Workflow Studio speaks both.」を、この文書の言葉で言い直したものです。

## 2. 価値の柱

製品価値を4本の柱に分解します。**2段目の機能マップは、この柱ごとにぶら下げます。**

各柱に「壊れたとき失うもの」を書いているのは、3段目の担保の優先順位が
そこから決まるためです。

### 柱1 — 設計と実行の断絶をなくす

**約束していること**: キャンバスで描いた構造が、推測を挟まずに、エージェントが
実行できる形式(`.claude/`, `.codex/`, `.cursor/` などのスキル/エージェント
ファイル)になる。

**なぜ求められるか**: 設計と実装が同じ一つの成果物になるので、「図では正しいが
プロンプトが間違っている」という乖離が原理的に起きない。

**壊れたとき失うもの**: 生成物がキャンバスと食い違えば、この製品を使う理由が
消滅します。ユーザーは食い違いに気づかないまま実行するため、**被害は本人の
手元ではなく、エージェントが動いた先で顕在化**します。

### 柱2 — エージェント的な仕事を設計できる

**約束していること**: 単なるフローチャートではなく、AI エージェント特有の
構成要素を組み立てられる。現在13種のノードがあり、性質ごとに分かれています。

| 分類 | ノード | 何のためにあるか |
|---|---|---|
| 制御 | `start` `end` `ifElse` `switch` | 実行順序と分岐 |
| 実行主体 | `prompt` `subAgent` `subAgentFlow` `codex` | 本体で実行するか、隔離したサブエージェントに委ねるか |
| 能力の呼び出し | `skill` `mcp` | Claude Code Skill / 外部 MCP ツールの利用 |
| 人間の介在 | `askUserQuestion` `branchSession` | 選択肢の提示、人間による確認の割り込み |
| 整理 | `group` | 実行に影響しない視覚的まとまり |

**なぜ求められるか**: サブエージェントへの委譲、Skill の呼び出し、人間の
確認ポイントといった「エージェント的設計(agentic engineering)」の語彙が
最初から揃っているので、設計者はそれらの組み合わせに集中できる。

**壊れたとき失うもの**: 表現力が落ちれば、実務のワークフローが表現しきれず、
結局プロンプトを手書きすることになります。製品を使う動機そのものが目減りします。

### 柱3 — 入口とエージェントを選ばない

**約束していること**: 一つの `workflow.json` を、3つの入口から等価に扱える。
そして8種類のエージェント向けに書き出せる。

| 入口 | 用途 |
|---|---|
| VSCode 拡張 | 視覚的に設計する。最も操作しやすい入口 |
| CLI (`ccwf`) | 端末・CI・SSH・Codespaces。render / validate / export / run / preview / canvas |
| MCP サーバー (`ccwf-mcp`) | 外部の AI クライアントがワークフローを読み書きする |

書き出し先: Claude Code / GitHub Copilot Chat / Copilot CLI / OpenAI Codex CLI /
Zoo Code / Gemini CLI / Antigravity / Cursor

**なぜ求められるか**: 「VSCode 専用の道」が存在しないこと自体が価値です。
キャンバスで描いたファイルを CLI がそのまま描画し、外部の Claude Code が MCP
経由で同じファイルを編集できる。**エージェントを乗り換えてもワークフロー資産が
残る**ので、特定ベンダーへのロックインを避けられます。

**壊れたとき失うもの**: 入口ごとに解釈が食い違えば、この柱の前提が崩れます。
CLI で検証が通ったのに拡張では開けない、といった状態はユーザーの信頼を直接
損ないます。

### 柱4 — AI 自身が設計に参加できる

**約束していること**: MCP サーバー経由で、AI エージェントがワークフローを
読み、書き、検証できる。自然言語で「ここに分岐を足して」と頼める。

提供しているツール: `get_workflow` / `apply_workflow` / `patch_workflow` /
`validate_workflow` / `export_workflow` / `render_workflow`

**なぜ求められるか**: 設計そのものを AI に手伝わせられる。ゼロから描く負担も、
既存を改善する負担も下がります。`IMPLEMENTATION_PLAN.md` の価値軸2
「AI-editing quality」が指しているのはここです。

**壊れたとき失うもの**: この柱は**ユーザーのファイルを AI に預ける**という
信頼の上に成り立っています。預けた結果が壊れて返ってくる経験が一度でもあれば、
ユーザーは二度と AI 編集を使いません。柱の中で最も信頼が壊れやすい領域です。

## 3. すべての柱に共通する土台

柱ごとの機能とは別に、**どの柱でも前提になっている性質**です。3段目の担保では
ここが最優先になると考えています。

**ユーザーのワークフローファイルは、ユーザーの資産である。**
キャンバスの保存、`ccwf export`、MCP の書き込み —— どの経路を通っても、
妥当なファイルが残るか、明示的に失敗するかのどちらかであるべきで、壊れた
ファイルを黙って残してはいけません。他の失敗は不便で済みますが、これは
ユーザーが取り戻せないものを壊します。

**「成功した」という報告は真実である。**
検証が「妥当」と言い、コマンドが終了コード0を返したなら、実際にそうである
必要があります。偽の失敗より**偽の成功のほうが有害**です。ユーザーはその
結果を信じて次の行動を取るからです。

## 4. この製品が目指していないもの

価値の定義は、目指さないものを書いて初めて輪郭を持ちます。

- **汎用ワークフローエンジンではない。** 対象は AI コーディングエージェントの
  オーケストレーションであって、業務システムの一般的なジョブ実行ではありません。
- **実行基盤そのものではない。** 実行するのはエージェント側で、本製品は設計と
  成果物生成を担います(`run` はエージェントの起動までを担当)。
- **チャット UI での AI 編集は終息済み。** `RefinementChatPanel` /
  `AiGenerationDialog` は保守のみで、AI 編集は MCP サーバー経由が正式路線です
  (CLAUDE.md 参照)。

## 5. 下の階層をどう接続するか

2段目(機能マップ)は、柱ごとに次の形で列挙する想定です。

| 列 | 内容 |
|---|---|
| 機能 | ユーザーから見た機能の単位 |
| 実装箇所 | パッケージとモジュール |
| 支える柱 | 柱1〜4 のどれか |
| 失敗の見え方 | 壊れたときユーザーに何が起きるか。**気づけるか / 取り返せるか** |

最後の列が3段目(担保)の入力になります。**気づけない失敗・取り返せない失敗は
自動テストで守り、即座に気づいて回避できる失敗は手動E2Eに残す** という
振り分けを想定しています。

書き味を確認するための例(柱1・柱3 から1つずつ):

| 機能 | 実装箇所 | 柱 | 失敗の見え方 |
|---|---|---|---|
| ワークフローのエクスポート | `packages/core` 生成器 + `packages/cli` export | 柱1 | 生成物がキャンバスと食い違う。**気づけない・取り返せない** → 自動テスト必須 |
| キーボードショートカット | `packages/vscode` webview | 柱3(操作性) | 押しても反応しない。**即座に気づく・回避できる** → 手動E2E で十分 |

この振り分け基準が妥当かどうかも、1段目を確定させる際に併せてご判断ください。
